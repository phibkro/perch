# One setup per Perch workspace

**Research checked 7 October 2026.** This note separates the recommended setup
experience from provider and platform capabilities. No Cloudflare account or
provider subscription was authenticated during the research.

The initial implementation is now documented in [Cloud setup](CLOUD-SETUP.md):
`scripts/setup-cloudflare.mjs` implements the host wizard and Pi Durable discovery.
The [self-hosted setup](WORKSPACE-SETUP.md) discovers configured local adapters and
builds the shared gateway; operators still install, authenticate, and supervise
the chosen harnesses themselves. Recommendations below also describe later work.

## Product boundary

The phone should ask where the assistant runs: **Self-hosted** or **Cloud**.
Cloud defaults to the user's Cloudflare account. Both choices should finish with
one workspace pairing code. The workspace then advertises its available
harnesses, models, chats, and capabilities. Changing the model or harness inside
that workspace should not repeat the connection setup.

Keep execution, provider credentials, working directories, and recovery on the
host. Perch remains the chat and artifact client described in [DESIGN.md](DESIGN.md).
The device holds a workspace credential, distinct from infrastructure authority
and model-provider credentials. A pairing code containing a device token is a
secret capability; a later one-use enrollment flow can replace that initial
transfer without changing the workspace contract.

| User choice | Work performed away from the phone | Phone task |
| --- | --- | --- |
| Self-hosted | Install or discover harnesses; select their workspace; configure provider accounts, HTTPS, supervision, and storage; expose one Perch workspace endpoint | Import the host's pairing code and choose an advertised assistant |
| Cloudflare | Authorize deployment; create the Worker, SQLite Durable Object namespaces, and private R2 bucket; configure selected model providers; verify the endpoint | Complete account consent where required, then import the generated pairing code |

The shared [workspace protocol](../src/workspace/protocol.ts) is the boundary.
Discovery must require the same workspace bearer credential as chat. Connector
URLs should be relative paths on the trusted workspace origin, and metadata
must not disclose provider keys or upstream administrative credentials.

## Smallest credential set

| Credential or choice | Needed when | Where it belongs |
| --- | --- | --- |
| Cloudflare account selection | Provisioning cloud resources | Setup runner or Cloudflare's own deployment page; the account ID is not a secret |
| Cloudflare OAuth grant **or** account-scoped API token | Authorizing deployment | The setup runner; never an agent prompt or phone chat credential |
| OpenCode Go key | Go is selected | Host provider configuration; Pi names its variable `OPENCODE_API_KEY` |
| Anthropic API key | Direct Claude API access is selected | Host secret, conventionally `ANTHROPIC_API_KEY` |
| OpenAI API key | Metered OpenAI API access is selected | Host secret, conventionally `OPENAI_API_KEY` |
| Browser/device authorization | A supported subscription login is selected | The owning harness or provider integration manages its credential lifecycle |
| Perch workspace/device token | Pairing a phone | Generated by setup; stored by the host and securely on the paired device |
| S3 endpoint, access-key ID, and secret | A self-hosted runtime or Linux backup process uses R2 through S3 | That process's private configuration, scoped to the selected bucket |

The native Cloudflare Worker uses R2 and Durable Objects through bindings. It
does **not** need an S3 access-key pair or a Durable Object password. Those extra
credentials are relevant to an external S3 client, such as a self-hosted celld
fleet or a Linux backup process. [CF-R2-BINDING] [CF-R2-CLI]

Ask for only the providers the user selects. A Cloudflare account does not confer
an OpenCode, Anthropic, or OpenAI entitlement. A subscription key can have a
different billing route from the same vendor's metered API key. The existing
[provider audit](PROVIDERS.md) distinguishes catalog coverage from authenticated
access.

## Cloudflare authorization and provisioning

For a first deployment, current Workers authorization requires **Admin at the
Workers product scope** to create the Worker. Once it exists, a deployment token
can use **Editor for that Worker**. Editor covers code, secrets, and deployment
of bindings to existing resources. Durable Objects inherit authorization from
their implementing Worker; no separate DO role is required. Adding or changing
a custom domain also requires Workers Routes Write for the affected zone.
Using a `workers.dev` endpoint avoids that domain setup. [CF-WORKERS] [CF-DO]

Creating an R2 bucket is a separate action: the API currently lists
`Workers R2 Storage Write` as its accepted permission. This is broader than an
object-only token. A deployment that merely binds an existing bucket does not
need direct bucket/object permissions. Cloudflare's Workers role names changed
in September 2026; the API still documents some legacy permission names.
[CF-R2-CREATE] [CF-WORKERS]

Wrangler can use a supplied `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`.
For an interactive user, its supported device flow is especially useful on a
headless machine: `wrangler login --device --browser=false` prints a verification
URL and code, and waits for consent in the user's browser. It avoids forwarding a
localhost callback to the phone. Scope selection remains available; default
Wrangler login requests all available scopes. [CF-ENV] [CF-LOGIN]

### Practical first implementation

A repeatable host-side runner can make the existing backend concrete with these
stages:

1. Select the account, Worker and bucket names, workspace label, and provider.
2. Build the real backend and show the resource and credential destinations.
3. Require an explicit apply action before creating resources.
4. Create or explicitly reuse the private R2 bucket, configure both SQLite DO
   classes, and deploy the Worker with the model and workspace token as secrets.
5. Read authenticated health and workspace discovery from the deployed URL.
6. Emit the one pairing code only after the deployed endpoint passes those checks.

The runner should retain a private deployment record for retries, preserve the
workspace token across an update, and refuse to silently replace an unrelated
existing Worker. Resource names and completed stages let an interrupted setup
resume without deleting chat state. Build or upload failure must not produce a
success pairing message. Cloudflare supports deploying code and secrets together
using `wrangler deploy --secrets-file`; secrets absent from that file are
preserved. [CF-SECRETS]

This cloud route runs Perch's durable assistant. A full Pi CLI, OMP, OpenCode,
Codex, or Claude Code harness needs its ordinary host/runtime integration. The
included Pi bridge starts a subprocess, while Cloudflare's documented OpenCode
recipe runs in a Linux Sandbox. Containerizing a harness does not itself preserve
its files, credentials, pending approvals, or interrupted work. [CF-OPENCODE]

### Lower-friction browser setup

Cloudflare's **Deploy to Cloudflare** flow can clone a public template, configure
Workers Builds, provision R2 and Durable Objects, and collect Worker secrets.
It supports descriptions for each binding in `package.json` and discovers secret
names from `.dev.vars.example`. This is a useful future entry point for the
phone's Cloud button: Cloudflare handles its own login and provisioning authority.
[CF-DEPLOY]

The selected template must be self-contained. Cloudflare treats a selected
subdirectory as the new repository root. Perch's inspected backend imports the
shared protocol from the app repository, so a button aimed at
`server/pi-durable` without packaging those imports would fail. Use a root build
configuration or generate a standalone template from the canonical source. A
post-deploy authenticated pairing step is still needed. [CF-DEPLOY]

## Model access and subscriptions

| Route | Supported authentication | Appropriate initial integration | Boundary |
| --- | --- | --- | --- |
| OpenCode Go | Subscription API key | Host Pi/OpenCode provider, or a tested Go-compatible Pi Durable adapter | Coding-agent service; retain the correct Go endpoint and session headers |
| Anthropic API | User's API key or a documented cloud-provider credential | Pi/OMP/OpenCode host, or native Anthropic Messages provider in Pi Durable | API billing is separate from Claude subscription allowance |
| Claude subscription | Anthropic's own sign-in in its unmodified Claude Code binary | A distinct hosted Claude Code harness integration | Do not import its consumer OAuth tokens into Perch, Pi, or OpenCode |
| OpenAI API | User's Platform API key | OpenAI Responses adapter or a host harness | Metered API access, separate from ChatGPT subscription access |
| Codex with ChatGPT | Codex's own browser or device flow | Host-owned Codex app-server; OpenCode also documents a ChatGPT login | Requires provider consent and durable host credential handling |
| Sign in with ChatGPT for OSS | Explicit grant for eligible Responses API requests | A separately verified OSS/self-hosted integration | Public-client registration and runtime restrictions apply; not a generic static API key |
| Local model | Configured endpoint and optional key | Self-hosted Pi or compatible API provider | The host establishes reachability and actual tool-call compatibility |

### OpenCode Go

OpenCode explicitly supports Go from other coding agents, including current Pi
builds. Clients need an identifying user agent and stable conversation identity;
the standard header is `x-opencode-session`. Go's model list includes several API
families, so an OpenAI-completions-only adapter covers only that subset. The Go
request paths are under `/zen/go/v1`; `/zen/v1` is the separate Zen route. In the
installed Pi catalog, the Anthropic SDK's base URL is `/zen/go` because that SDK
adds `/v1/messages`; Completions and Responses use a `/zen/go/v1` base. The
implemented wire tests exercise both roots under one provider. Preserve the
selected billing path and show subscription-limit failures instead of silently
falling back to paid credits. [GO]

### Anthropic

Anthropic's primary documentation distinguishes two cases. Developers offering
their own app must use API keys or supported cloud-provider credentials, and must
not collect, store, or intermediate Claude.ai subscription credentials. Users may
sign in with their own subscription to an **unmodified Claude Code binary**, even
when another platform hosts it, subject to the documented hosting conditions.
That is a separate harness integration, not permission to reuse its tokens in
another agent loop. [ANTHROPIC-AUTH]

OpenCode's current provider page contains a stale paragraph about Pro/Max login,
followed by an explicit notice that its bundled Anthropic subscription plugins
were removed as of 1.3.0. The first-party Anthropic policy determines the design;
do not present the stale paragraph or an upstream OAuth implementation as a
permission grant. [OPENCODE-PROVIDERS]

### Codex and the newer ChatGPT flow

Codex supports API-key and ChatGPT login. Its documented app-server method
`account/login/start` accepts `chatgptDeviceCode` and returns a verification URL,
user code, and login ID. The phone can show those values while the host owns the
login and subsequent authenticated runtime. The CLI has an equivalent device
login; the relevant account/workspace setting must permit it. [CODEX-SERVER]
[CODEX-AUTH]

There is also a newer, separate **Sign in with ChatGPT** flow for open-source and
locally hosted apps. It uses public-client registration without a client secret
or partner API key, a stable host ID, PKCE, state, nonce, and ID-token validation.
Only a grant containing `chatgpt.tokens.use.direct` authorizes plan usage.
Retain each issued client ID with the verified account, and replace rotating
credentials atomically. The documented callback is HTTP loopback on `127.0.0.1`.
[SIWC-SIGNIN]

OpenAI documents a self-hosted VM path: finish sign-in locally, transfer the
selected protected credential record securely, retain the VM's distinct host
identity, and let the VM own refreshes. The overview directs paid or remotely
hosted app offerings to an interest form. This research does not establish that
a centrally operated Perch cloud service, or a particular personal Workers
deployment, is approved for that offering. [SIWC-VM] [SIWC-OVERVIEW]

This newer route calls the public Responses API and requires streaming with
`store:false`; it is not a generic ChatGPT backend endpoint. Its preview excludes
several normal Responses parameters and hosted tools, and HTTP requests must
supply their conversation context. Account-specific model discovery and explicit
usage-limit handling belong on the host. [SIWC-INFERENCE] [SIWC-LIMITS]

Pi 1.0.4 includes the newer login under provider `openai` and labels
`openai-codex` as legacy. Its CLI authentication uses Node facilities. Pi AI's
`CredentialStore.modify` serializes refreshes, which is the appropriate seam for
a future host credential service. A Worker adaptation still needs a runtime-safe
login/refresh implementation and a provider conformance test. [PI-AI]

## What belongs on the self-hosted machine

Bootstrap should discover installed harnesses and ask which to expose. It should
reuse an explicitly selected host profile, configure supervision and HTTPS, and
put all selected adapters behind one authenticated workspace endpoint. The
existing OpenCode gateway remains necessary because the inspected upstream
provider API can expose provider credentials; discovery must project safe model
metadata rather than forward that API wholesale. [OPENCODE-LOCAL]

For ordinary Pi, preserve its credential store and selected session across
process restarts. For celld, configure the actual bucket durability policy and
qualified object-store credentials on the host. Configure model endpoints from
the host's perspective: a phone must not receive a loopback model URL and be
expected to route to it. Recovery evidence and limits remain in
[DURABLE-BACKEND-RESULTS.md](DURABLE-BACKEND-RESULTS.md).

The first phone pairing can be a private copy-and-paste capability. A later
enrollment service should use a short-lived one-use code, issue revocable device
credentials, and retain an independently authorized admin route. One workspace
does not imply that every device should receive deployment rights. Provider
account management can open a protected host setup page while ordinary chats
continue using only the device's narrower credential.

## Delivery and verification boundary

Local tests can verify strict profile parsing, authenticated discovery, provider
wire formats, secret-free plan output, application ordering, refusal to overwrite
unknown resources, and restart-safe setup records. They cannot establish account
entitlement, actual Cloudflare provisioning, R2 durability, or OAuth consent.
Those outcomes should appear as separate setup results after the real operations
complete. Do not mark a provider connected merely because its key has the right
shape or its name appears in a catalog.
